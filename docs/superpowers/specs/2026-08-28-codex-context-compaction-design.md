# Agent Pi DSH 3.3.5：Codex 指派、模型容量与自动压缩设计

日期：2026-08-28
状态：已确认，待实施计划
目标版本：3.3.5

## 1. 背景

Agent Pi DSH 已以 DeepSeek Harness（DSH）作为主智能体内核。Codex 的定位不是替换 DSH，也不是把 Windows Codex 桌面窗口嵌入应用，而是由 DSH 按需启动官方 Codex CLI/app-server，作为独立子智能体完成一项明确任务并把结果交回主对话。

当前存在三类相关问题：

1. 用户无法在主对话中明确指定“这一轮交给 Codex 执行”。
2. 新增或自定义模型的上下文长度可能缺失或沿用保守默认值，长程任务无法可靠判断剩余容量。
3. DSH 虽已启用自动压缩，但真实会话中的压缩曾因当前模型上下文溢出、请求中止或摘要达到输出上限而失败，最终只能新建对话。

本设计在不改变 DSH 主智能体地位的前提下，补齐 Codex 显式指派、模型容量识别和自动压缩兜底。

## 2. 目标

### 2.1 功能目标

- 在主对话输入区提供一次性的“Codex 执行”控制；开启后，仅下一条消息由 DSH 明确委派给 `subagent_codex`。
- ChatGPT/Codex 登录成功后，读取 Codex 运行时的实际默认或当前模型标识，并为已核实模型匹配上下文与最大输出长度。
- 新增或自定义供应商、模型时，尽可能自动取得真实容量；无法确认时显示来源和“估算”状态，避免把估算值伪装成官方值。
- 将 DeepSeek 官方三个 DSH 模型的容量统一为 1,000,000 上下文、384,000 最大输出。
- 将自动压缩触发阈值调整为上下文使用率约 72%，优先使用当前模型摘要；当前模型压缩失败时，允许使用 DeepSeek V4 Flash Vision Exp 兜底。
- 所有变更继续以 3.3.5 版本测试、打包和发布，不提升版本号。

### 2.2 非目标

- 不把 Codex 注册成 DSH 的普通聊天模型供应商。
- 不将 Windows Codex 桌面应用嵌入 Agent Pi DSH 窗口。
- 不迁移旧 Agent Pi 的 Pi 主运行循环。
- 不在应用运行时抓取任意供应商官网网页来推测模型参数。
- 不保证任意第三方兼容接口都能提供准确容量；没有可靠元数据时必须使用可见的保守估算。
- 不在本次工作中重构投标流程或与本需求无关的界面和内核代码。

## 3. 已确认的产品决策

### 3.1 DSH 与 Codex 的职责

DSH 保持主智能体、会话上下文持有者和投标流程控制者。Codex 是一轮一任务的子智能体：DSH 整理任务说明、相关文件路径、必要知识和交付目标，调用 `subagent_codex`，等待其完成，再由 DSH 检查结果并向用户汇报。

Codex 子智能体不自动继承父对话、父知识库或全部工作区背景。需要的上下文由 DSH 在每次委派时显式提供。

### 3.2 模型容量来源优先级

同一模型出现多个容量来源时，按以下顺序选择：

1. 用户在模型设置中明确填写的数值。
2. 当前供应商或部署端 `/models` 等接口返回的容量元数据。
3. 应用内置、按精确模型 ID 匹配的已核实官方目录。
4. 路由的保守默认值：上下文 262,144，最大输出 32,768。

部署端元数据高于通用官方目录，因为第三方网关或具体部署可能对原模型施加更小限制。只允许精确模型 ID 或已明确维护的别名匹配；不得用模糊字符串匹配把相近型号误判为同一容量。

每个最终值需要携带来源状态，至少区分：

- 用户设置
- 供应商返回
- 官方目录
- 保守估算

当使用保守估算时，设置界面必须明确显示“估算”，不能显示成已确认容量。

### 3.3 DeepSeek 官方模型容量

以下三个精确模型 ID 使用相同的官方容量：

| 模型 ID | 上下文长度 | 最大输出长度 |
| --- | ---: | ---: |
| `deepseek-v4-flash` | 1,000,000 | 384,000 |
| `deepseek-v4-pro` | 1,000,000 | 384,000 |
| `deepseek-v4-flash-vision-exp` | 1,000,000 | 384,000 |

初始化新配置时写入这些值；已有 3.3.5 配置在启动或配置修复阶段补齐缺失值，但不得覆盖用户已明确修改的容量。

### 3.4 Codex 登录后的模型识别

应用继续使用随安装包提供的官方 Codex CLI/app-server，通过系统浏览器完成 ChatGPT 登录，不需要 API Key。登录成功或用户刷新状态时：

1. 启动应用专属 Codex home 下的 app-server。
2. 请求模型列表并读取 `isDefault` 或当前已选择的模型 ID。
3. 若 app-server 直接返回容量，按供应商返回值使用。
4. 若未返回容量，按精确模型 ID查询应用内置的已核实 OpenAI 模型目录。
5. 若仍未知，显示模型 ID，并将容量标为保守估算，不阻断 Codex 使用。

当前已验证的默认模型 `gpt-5.6-sol` 在内置目录中记录为 1,050,000 上下文、128,000 最大输出。ChatGPT Pro 订阅本身不被硬编码成某个容量；容量始终跟随实际模型 ID。

## 4. 主对话“Codex 执行”交互

### 4.1 用户流程

- 主输入区增加“Codex 执行”一次性开关，默认关闭。
- 用户打开后发送消息，该条消息仍进入 DSH 主会话，但附带确定性的委派意图。
- DSH 必须立即以前台模式调用 `subagent_codex`，即 `run_in_background=false`；不得先自行完成同一任务后再把 Codex 当作装饰性复核。
- DSH 等待 Codex 返回，检查其输出或文件变更，再在原对话中汇报。
- 消息成功提交后开关自动恢复关闭，下一条消息重新走普通 DSH 流程。

### 4.2 提交与失败行为

- 如果消息未成功提交，开关状态保留，避免用户重试时意图丢失。
- 如果 Codex 未登录或运行时不可用，提交前给出明确提示并保留输入内容，不静默回退到 DSH 自行执行。
- 如果 Codex 子任务启动后失败，DSH 在原对话中报告实际错误；不自动切换成其他模型重做，除非用户再次指示。
- 普通消息、已有输入附件和权限设置不因开关而改变。

### 4.3 委派指令

界面层只加入最小、稳定的结构化委派提示，表达以下约束：

- 立即调用 `subagent_codex`。
- 使用前台执行并等待结束。
- 将用户原始任务、明确文件路径、必要上下文和验收目标完整交给 Codex。
- Codex 返回后检查交付结果，再向用户答复。

不得依赖自然语言猜测用户是否“可能想用 Codex”；只有一次性开关开启时才强制委派。

## 5. 自动压缩与跨供应商兜底

### 5.1 触发策略

- 保持自动压缩开启。
- 将自动触发阈值从默认 80% 调整为约 72%，为工具调用、附件和下一轮输出留出余量。
- 保留手动 `compact` 命令，作为用户主动控制入口。
- 容量计算使用第 3.2 节解析出的最终上下文长度；如果只能估算，则以估算值保守触发。

### 5.2 两级摘要链路

自动或手动压缩使用同一条链路：

1. 首先使用当前会话模型生成摘要，保持供应商一致性。
2. 若当前模型因上下文溢出、摘要达到输出上限而不完整、模型不可用或内容类型不支持而失败，则调用 DeepSeek 官方 `deepseek-v4-flash-vision-exp` 生成兜底摘要。
3. 兜底摘要最大输出设为 32,768 tokens，以提高完整性，同时避免直接放开到模型的 384,000 最大输出。
4. 只有得到完整、可用的摘要后，才写入压缩结果并替换旧历史；任一级失败都不得留下半完成压缩状态。

兜底选择 Vision Exp，是因为历史消息可能含图片；它可以覆盖纯文本和图像会话。产品文案仍以“DeepSeek V4 Flash 摘要兜底”描述，并在详细信息中显示实际模型 ID。

### 5.3 允许与禁止兜底的错误

允许触发 DeepSeek 兜底：

- 当前模型报告上下文溢出。
- 摘要因输出上限截断或缺少完整检查点。
- 当前模型暂时不可用或拒绝当前历史中的内容类型。
- 当前模型摘要请求发生可重试的供应商错误，且当前模型自身重试已耗尽。

禁止触发 DeepSeek 兜底：

- 用户主动取消或中止压缩。
- 应用正在关闭。
- 没有可用的 DeepSeek 官方凭据。
- 错误表明请求内容违反供应商政策。

用户取消必须立即停止，不得以“提高成功率”为由把历史发送给另一个供应商。

### 5.4 隐私、费用与可见性

用户已明确同意：当前模型压缩失败时，可将待摘要的旧对话发送给 DeepSeek V4 Flash Vision Exp；这会产生一次 DeepSeek 调用费用，并使该段对话跨供应商处理。

设置页需要说明这一行为，并提供启用状态。3.3.5 对本项目的默认初始化配置启用该兜底；若用户关闭，系统只尝试当前模型。压缩事件或错误提示必须能区分“当前模型摘要”和“DeepSeek 兜底摘要”，方便排查费用与失败原因。

如果 DeepSeek 凭据缺失或兜底仍失败：

- 保持原会话历史不变。
- 显示可操作的错误，指出是当前模型失败、兜底不可用或兜底失败。
- 允许用户重试手动压缩、调整模型容量或新建会话。

## 6. 数据流

### 6.1 模型配置

1. 用户新增供应商或刷新模型。
2. 读取供应商返回的模型列表和容量字段。
3. 对缺失字段按精确模型 ID 查询内置官方目录。
4. 对仍缺失字段使用保守默认值。
5. 在模型设置和运行时暴露最终值及其来源。
6. token meter 与 compaction-basic 使用同一个最终上下文长度，避免界面显示和实际触发阈值不一致。

### 6.2 Codex 指派

1. 用户打开一次性“Codex 执行”开关并提交消息。
2. 提交前确认 Codex 运行时可用且已登录。
3. DSH 收到带委派意图的原始任务。
4. DSH 整理必要上下文，前台调用 `subagent_codex`。
5. Codex CLI/app-server 在独立运行时完成任务。
6. DSH 检查结果并在原会话答复。
7. 开关在成功提交后复位。

### 6.3 自动压缩

1. token meter 根据最终模型容量计算使用率。
2. 使用率达到约 72% 时触发 compaction-basic。
3. 当前模型先生成摘要。
4. 当前模型发生允许兜底的失败时，调用 DeepSeek Vision Exp。
5. 完整摘要成功后原子写入压缩结果；失败则保留原历史并给出可见错误。

## 7. 配置与迁移

### 7.1 新配置

3.3.5 新生成的投标配置包含：

- DeepSeek 三个官方模型的 1,000,000 / 384,000 容量。
- 自动压缩阈值约 72%。
- 当前模型优先、DeepSeek Vision Exp 第二级的摘要链路。
- 已启用的跨供应商兜底说明。
- Codex 子智能体继续使用应用专属 Codex home 与 ChatGPT 登录。

### 7.2 已有配置

迁移或修复逻辑只补齐本项目管理的字段：

- 对三个精确 DeepSeek 模型补齐缺失的上下文和最大输出值。
- 对缺失的自动压缩配置写入 72% 与兜底设置。
- 保留用户明确设置的容量和用户主动关闭的兜底选项。
- 不删除自定义供应商、模型或其他用户设置。

迁移必须可重复执行；第二次启动不得继续改写相同配置或制造重复模型条目。

## 8. 错误处理与诊断

- Codex 状态至少区分：运行时缺失、未登录、已登录、状态探测失败。
- Codex 模型容量未知不等于运行时不可用；允许执行，但明确标为估算容量。
- 模型发现失败不得删除已有模型配置。
- 自动压缩失败不得损坏会话或丢失消息。
- 压缩诊断记录当前模型尝试结果、是否进入 DeepSeek 兜底、最终采用的摘要模型和失败类别，但不得记录登录凭据。
- 所有用户可见提示使用非技术语言，同时保留足够的详细错误供排查。

## 9. 验收标准

### 9.1 Codex

- 安装版设置页可正确识别随包 Codex 运行时，并能通过系统浏览器完成 ChatGPT 登录。
- 登录后显示实际默认或当前 Codex 模型；已知模型显示已核实容量，未知模型显示估算状态。
- 主对话开启“Codex 执行”后，下一条消息只触发一次前台 `subagent_codex` 委派，成功提交后开关复位。
- Codex 不可用时保留用户输入并明确阻止该次委派。
- 普通消息路径不受影响。

### 9.2 模型容量

- DeepSeek 三个精确模型均显示 1,000,000 上下文、384,000 最大输出。
- 用户手工容量不会被目录或发现结果覆盖。
- 供应商返回的部署容量优先于通用官方目录。
- 未知自定义模型显示 262,144 / 32,768 的保守估算及“估算”来源。
- 已有配置迁移可重复执行且不产生重复条目。

### 9.3 自动压缩

- 使用率达到约 72% 时自动触发压缩，低于阈值时不触发。
- 当前模型摘要成功时不调用 DeepSeek 兜底。
- 当前模型发生上下文溢出或摘要截断时，使用 `deepseek-v4-flash-vision-exp` 兜底并只提交一个最终摘要。
- 用户取消时不调用 DeepSeek。
- DeepSeek 凭据缺失或两级均失败时，原历史保持不变并显示明确错误。
- 含图片的旧历史可以进入 Vision Exp 兜底链路。

### 9.4 回归与发布

- 桌面端 Codex 认证/桥接测试通过。
- 模型发现、容量优先级、配置迁移和未知模型估算测试通过。
- compaction-basic 的当前模型成功、允许兜底、禁止兜底、两级失败和原子写入测试通过。
- 主输入区普通提交与 Codex 一次性提交测试通过。
- Windows 安装包重新构建并做安装态烟雾验证。
- GitHub 3.3.5 发布资源按现有跨平台流水线重新生成或触发，并核对 Windows、macOS、Linux 资源完整性。

## 10. 实施约束

- 采用测试先行：先建立能复现问题或表达新行为的失败测试，再写最小实现。
- 修改范围限制在 Codex 桥接/设置与主输入区、模型容量解析与投标配置修复、compaction-basic 及对应测试和发布配置。
- 不清理工作区中与本需求无关的既有改动，尤其不覆盖 `vendor/deepseek-harness` 内已有用户修改。
- 规格提交与功能实现提交分离；功能实现前先形成逐文件实施计划。

## 11. 依据与假设

- DeepSeek 三个模型的 1M 上下文和最大 384K 输出依据用户提供的 DeepSeek 官方页面截图，并与当前官方定价/模型说明保持一致。
- Codex app-server 的模型列表可能只返回模型 ID而不返回容量，因此需要内置已核实目录作为第二来源。
- `gpt-5.6-sol` 的 1,050,000 上下文和 128,000 最大输出来自 OpenAI 官方模型文档。
- 任意第三方供应商不存在统一、强制的容量发现协议；“自动匹配”定义为尽最大可能使用可靠元数据，并对无法确认的值明确标注估算。
- DeepSeek 兜底依赖用户已配置可用的 DeepSeek 官方凭据；凭据缺失时不得绕过认证或改用其他未授权供应商。
